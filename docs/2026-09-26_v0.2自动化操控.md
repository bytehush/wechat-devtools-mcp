# v0.2：自动化操控运行中的小程序

状态: 已实现
取代: 无（v0.1 记录见 [2026-09-25_立项与v0.1最小集.md](./2026-09-25_立项与v0.1最小集.md)，其结论仍有效，本文只补充 v0.2 增量）

## 缘起

v0.1 交付后继续 v0.2：让 agent 能操控**运行中的**小程序（读页面数据、触发交互、
截图、读控制台），形成"改代码 → 看运行效果 → 读报错"的调试闭环。

需求一句话：agent 能对运行中的小程序完成"看状态、触发交互、看报错、留截图"四件事。

## 替代方案及为何不选

| 方案 | 不选原因 |
|---|---|
| 用 SDK 自带的 `automator.launch()` | 实测在高版本 Node 上失败：它内部裸 `spawn(cli.bat)`，Node ≥18.20 因安全限制直接 EINVAL，错误被吞成"cliPath 不正确"。改为自跑 `cli auto`（runCli）+ `automator.connect({wsEndpoint})` |
| 元素级 DOM 操作（`Page.getElements` / `element.tap` / `element.input`） | 实测在 IDE 2.01.2510290 + automator npm 0.12.1 下不可用（详见下文排查），改用 `call_method` + `evaluate` 承担同等职责 |
| 继续硬啃 IDE 打包代码（core.wxvpkg）逆向协议 | 成本失控；社区新一代工具（weapp-agent-mcp、wxpilot 等）同样绕开传统 automator 脚本调用，证明此路非本项目的职责 |

## 排查实录（为何砍掉元素级工具）

对"页面级命令无响应"做了 7 组对照实验，事实链：

1. 连接、导航（App.reLaunch）、截图（App.captureScreenshot）、控制台流（App.enableLog）全部正常——WS 通道与 IDE 侧命令都活着
2. `page.data()` / `page.$$()` 挂死到超时（最初现象）
3. 强杀 IDE → `cli auto` 全新启动 → 页面级命令改为**秒回** "page node not found"——后端处理链存在，但页面节点未注册
4. 连接后先 `reLaunch`（页面 id=2 新建）→ `page.data()` 仍挂死——新页面已注册但 appservice 侧代理不应答
5. `--trust-project`、二次 `cli auto` 重初始化、重连——均无效
6. `Tool.getInfo` 显示 IDE 2.01.2510290 / SDKVersion 3.16.3；npm 端 automator 0.12.1 停更于 2023-11——协议代差是根因
7. **`miniProgram.evaluate` 完全可用**：在 appservice 上下文执行任意函数并返回序列化结果（`App.callWxMethod` 也正常——systemInfo 有返回）

结论：IDE 侧页面注册表与 appservice 代理之间的 Page.* 转发在该版本组合下损坏，
但 appservice 通道完好。因此页面级能力全部改走 `evaluate`：

- `get_page_info` = `evaluate(() => getCurrentPages()...)` 读路径/栈/data
- `call_method` = `evaluate` 调用页面方法（bindtap 的处理函数），等效模拟点击
- `wx_method` = 原生 `App.callWxMethod`（实测可用）

**收尾时的安全取舍**：最初还暴露了一个万能 `evaluate` 工具（agent 可执行任意
appservice JS）。Mimosa 提交门禁判为"代码注入"高危（`new Function(agent字符串)`
在语义上确实如此）。评估后主动移除该工具：结构化的 `call_method` / `get_page_info` /
`wx_method` 已覆盖调试闭环，任意代码执行面的收益不值得它的风险。工具总数 13 → 12。

## 实现

- `src/automation.js`：会话管理（同一时间一条连接；换项目先断旧）+ 各操作封装，
  全部带超时包装；启动流程 = `runCli(["auto", ...])` → `connectWithRetry`（60s 内每 1.5s 探测）。
  `automation_stop` 用 `disconnect`（IDE 保持运行，不强行关闭用户窗口）。
- `src/index.js`：注册 9 个自动化工具（合计 13 个工具）。
- 自动化端口默认 9421，可用 `WECHAT_DEVTOOLS_AUTOMATION_PORT` 覆盖。
- 测试小程序 `fixtures/demo-miniprogram` 增加 `onLoad` console.log 与 onTap 日志，便于验证控制台捕获。

## 验证（本轮实际跑过的命令与输出）

1. 语法关：`node --check` 全部源码 → 通过
2. 冒烟：`npm run smoke` → **26 通过，0 失败**，其中自动化全链路（真实 IDE）：
   - `automation_start` → `navigate` → `get_page_info` 读到 data（含欢迎语）
   - `call_method("onTap")` → `get_page_info` 显示 `tapCount: 1`（状态真实变化）
   - `wx_method("getSystemInfoSync")` 返回平台信息
   - `screenshot` 生成于项目目录内；`console_logs` 捕获到 "demo page loaded"
   - `automation_stop` 断开
   - 错误路径：未建会话调 `navigate` → 明确指引先调 `automation_start`
3. 反证关：把 `tapCount` 期望值改错 → 红（26 通过 1 失败，恰好断在该断言）；还原 → 绿（27/0；
   移除 evaluate 工具后复测 26/0）
4. 截图留档：simulator 画面正确渲染测试页面（"Hello, wechat-devtools-mcp!" + 按钮），证明自动化期间页面真实可用

**未验证（待用户手验）**：在真实 AppID 项目上验证 preview/upload 成功路径（v0.1 遗留，同前）。

## 边界与后续

- 元素级 DOM 操作（选择器查元素/DOM 点击/输入）当前不可用——受官方 npm SDK 停更所限；
  待官方发新包或确认其他 IDE 版本可用后再补

  只放行 `WECHAT_DEVTOOLS_MCP_ALLOWED_ROOTS` 内的项目
