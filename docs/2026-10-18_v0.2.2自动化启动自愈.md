# v0.2.2：自动化启动自愈（IDE 代启 + 端口实测判据）

状态: 已实现并实测
取代: 无（[2026-09-26_v0.2.1适配新版工具布局.md](./2026-09-26_v0.2.1适配新版工具布局.md) 的调用链结论不变，本文只写增量）

## 缘起

现象：`cli auto` 停在 `preparing` 不动，拿不到模拟器截图；同一条命令在 9 月是通的。

关键事实校正：`preparing` **不是阶段名**，是官方 CLI 所有子命令共用的 spinner 文案
（`islogin` / `open` / `preview` / `upload` / `auto` 全部打印它）。真实等待点是
`wait IDE ws port timeout`。所以"卡在 preparing"等于"命令发出去了，IDE 没回传自动化端口"。

## 根因（证据链）

1. **CLI 端不读注册表**。`resources/app.asar.unpacked/js/common/cli/index.js` 中
   `HKEY` / `winreg` / `registry` / `reg.exe` 全部 0 命中。它发现 IDE 靠
   `User Data\<hash>\Default\.ide` 里的端口 + `127.0.0.1:3799` 探测。
2. **reg.exe 是 IDE 侧调的**。`grep -a app.asar` 命中 4 处，全部来自 IDE 加载的 npm 模块：

   | 调用 | 来源 | 用途 |
   |---|---|---|
   | `reg query HKLM\SOFTWARE\Microsoft\Cryptography /v MachineGuid` | machine-id 类 | 设备指纹 |
   | `reg query ...\CentralProcessor\0 /v FeatureSet` | systeminformation | CPU 指令集 |
   | `reg query HKLM\...\AppModelUnlock` | VS Code 内核 | Windows SDK 检测 |
   | `reg query HKCU\Environment /v PATH` | VS Code 内核 | 环境变量写入 |

3. **拦截发生在 agent 的进程树内**。对照实验：沙箱外跑同一条 `cli auto`，
   `- preparing` 之后立即触发 `reg.exe` 拦截，进程收到 SIGTERM，提示明确写
   "This block cannot be approved or bypassed from the current command" ——
   禁用命令沙箱也绕不过 Program Blacklist 这一层。
4. **IDE 日志印证卡点**：`WeappLog/logs/` 中当日 4 次 CLI 启动均为
   `hasUser: true`（登录正常）、`startedByCLI, skip openLastModifiedProject`、
   `[cliService] start ws server at 15276 / 55256`（服务起来了），
   但**没有任何 `RENDERER_PROJECT opened`、没有 project 窗口**，日志止于
   `[ideplugin] use onlinePluginInfo`。即 IDE 启动到插件初始化后不再推进。

因果链：`CLI spawn IDE` → IDE 启动即读 `MachineGuid` → 子进程 `reg.exe` 被程序黑名单拦
→ 该步骤 Promise 悬住 → 项目窗口不创建 → 自动化 ws 端口永远不出现 → CLI 转圈 `preparing`。

## 实现

改动集中在"让 IDE 脱离 agent 进程树 + 用端口实测判就绪"。

- `src/config.js`：新增 `getIdeExePath()`。electron 布局下 CLI 的宿主程序即 IDE 主程序；
  旧版布局另按 >50MB 规则找。找不到返回 `null`，由上层给出"请手动打开"的指引。
- `src/automation.js`：
  - `readIdePorts()`：扫 `LOCALAPPDATA` 下 `微信开发者工具` / `微信web开发者工具` 两个目录名，
    收集所有 `User Data\<hash>\Default\.ide` 记录的端口（可能多实例并存）。
  - `probePort()`：`net.connect` TCP 探测，超时 300ms。**只认端口实测可连**——
    `.ide` 文件在 IDE 未运行时仍留着上次的陈旧端口（实测一直是 37075），不能作为判据。
  - `findAliveIdePort()`：并发探所有候选，返回第一个活的。
  - `launchIdeViaExplorer()`：`spawn("explorer.exe", [exePath], {detached, unref})`。
    Explorer 代启的进程挂在用户会话下，不再是 agent 的子进程，故不受程序黑名单连带管辖。
    **不判返回值**——实测成功时 explorer 也返回 1。
  - `ensureIdeRunning()`：已活则 0 等待返回；否则代启 + 200ms 轮询端口，60s 超时报可读错误。
  - `startSession()`：在 `cli auto` 之前先调 `ensureIdeRunning()`。这一步是必须的——
    IDE 不在时直接发 `cli auto`，CLI 会自己去 spawn IDE，正好走回被拦死的老路。
    返回文案里如实带上"是否代启、就绪耗时、IDE http 端口"。

## 验证（本轮实跑）

| 场景 | 结果 |
|---|---|
| 语法 | `npm run check` 全通过 |
| **冷启动**（IDE 完全没运行） | 代启 → **端口就绪 1931ms**；端到端（含 cli auto + 连接 + 就绪探测）12644ms |
| **热路径**（IDE 已在跑） | 识别"已在运行"、0 等待；端到端 9708ms |
| 回归 | `npm run smoke` → **26 通过 / 0 失败** |
| IDE 存活 | 命令结束后 38 个进程、37075 与 25086 均 LISTENING，未被沙箱清理连带杀掉 |

**关于"14 秒"**：此前测到的 14s 是"30 个进程全部起齐"的时间，不是可用时间。
换成端口实测判据后，真实下界是 **1.9s**。端到端剩余的大头（约 7-9s）在
`cli auto` 打开项目并编译，不属于启动等待，压不动也不该压。

## 边界与后续

- 代启的 IDE 会走 `openLastModifiedProject`（自动打开上次项目），随后 `cli auto` 再切到
  目标项目，多一次窗口切换——无功能影响。
- 若 IDE 主程序路径探测失败（非标准安装），`getIdeExePath()` 返回 null，会直接报
  "请手动打开开发者工具"，不会去猜路径。
- 未处理：`connectWithRetry` 间隔 1500ms、就绪探测间隔 1000ms 仍偏保守，若要再压 1-2 秒
  可调小；本轮不动，避免增加无谓重试。
